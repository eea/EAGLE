# How EAGLE Eye Came About

This document outlines the origin and technical evolution of the **EAGLE Eye** prototype: the authoritative sources integrated into its knowledge base, the preprocessing steps used to unify them, the pipeline that translates free-text class descriptions into structured EAGLE elements, and the export workflow that generates ISO 19144-2 Land Characterization System (LChS) XML. While the [README](../README.md) describes the current functionality of the application, this page documents its design rationale and underlying architecture.

## Motivation and Context

Land cover and land use class descriptions—such as those found in CORINE Land Cover (CLC), national legends, and field guides—are written in unstructured prose. By contrast, the EAGLE matrix represents the same concepts as a structured *bar code*: a combination of Land Cover Components (LCC), Land Use Attributes (LUA), and Land Characteristics (LCH), each assigned a Bar Code Value (BCV) that specifies its role within the class (e.g., excluded, optional, or selective mandatory).

Translating narrative definitions into EAGLE bar codes is traditionally a manual, expert-driven task. **EAGLE Eye** was developed as a prototype to assist with the first stage of this workflow: **highlighting the exact phrases in a description that correspond to EAGLE elements, proposing concrete classes and bar code values, enabling expert review and correction, and passing the validated result to a downstream ISO mapping tool.**

The prototype operates alongside a companion prototype, `eagle-iso-mapper`, which converts EAGLE barcoding matrices into ISO 19144-2 LChS XML and vice versa. EAGLE Eye was specifically designed to generate structured input for this downstream converter.

## Input Sources

Building the prototype required integrating structural spreadsheets, published semantic vocabularies, methodological manuals, reference class definitions, and target schema artifacts:

| Input Source | Description | Role in EAGLE Eye |
| --- | --- | --- |
| **EAGLE Barcoding Template 3.2** (`EAGLE Barcoding Template_3.2_20230829.xlsx`) | The core matrix containing the URI, code, label, and hierarchical level of every element | Supplies the complete catalog of 979 elements (56 LCC, 136 LUA, and 787 LCH) and their structural relationships |
| **EAGLE Matrix 3.2 Change-Log Workbook** (`...Old3.1.2-New3.2_20240606_corr.xlsx`) | Documentation of structural and semantic updates between versions 3.1.2 and 3.2 | Defines element types (*heading*, *parameter*, *character*) and land cover / land use (LC/LU) relevance |
| **Eionet EAGLE Vocabulary** (`dd.eionet.europa.eu/vocabulary/landcover/eagle`, CSV) | The official published semantic vocabulary | Provides formal definitions, *Includes* and *Excludes* notes, thematic domains, and parameter units |
| **EAGLE Bar Coding Manual (D3-1a, 2023) & Thematic Content Guidance (D3-1b)** | Methodological specifications for translating text into bar codes | Establishes the semantics of BCVs (`X`, `1`, `2`, `3`, `4`, `5`), the strict rule that *only explicit wording counts*, and the worked *Natural Grassland* benchmark |
| **CLC Illustrated Guide (Class 3.2.1)** | Practical nomenclature documentation illustrating real-world class descriptions | Defines document section semantics (*not applicable for*, *excludes*, *generalisation*, *particularities*) and provides a second reference text |
| **CLC 3.2.1 *Natural Grassland* Class Definition** | Primary benchmark text with an established reference bar code | Serves as the core validation example and the default sample text in the user interface |
| **`eagle-iso-mapper`** (LinkML model, SSSOM crosswalk, Excel-to-XML converter) | Companion transformation prototype | Handles the conversion of EAGLE barcoding matrices into ISO 19144-2 LChS XML |
| **Sample LChS XML** (generated by the FAO LChS tool) | Reference output in the target format | Verifies structural compatibility with the FAO LChS import specification |

Two of these inputs played a particularly decisive role in shaping the prototype's design:

* **The Worked *Natural Grassland* Benchmark:** The bar coding manual's worked example for *Natural Grassland* (`grassland` = `3`; `rocky areas`, `trees`, `shrubs`, `scattered`, `nature conservation`, `shrub clearance` = `1`; `drained`, `irrigated`, `fertilized` = `X`) is the sole fully verified gold-standard reference available, making it the central regression test for the extraction and scoring heuristics.
* **Section-Aware Text Interpretation:** The CLC Illustrated Guide demonstrated that the *structural context* of a description is just as important as its terminology—for instance, a term appearing under *This class excludes:* carries the opposite semantic meaning of the same term appearing in the main class definition.

## Data Integration and Preparation

### 1. Building a Machine-Readable Vocabulary (`scripts/build_vocabulary.py`)

To create a unified knowledge base, a reproducible preprocessing script merges the three primary EAGLE data sources—the Barcoding Template 3.2, the 3.1.2–3.2 change-log workbook, and the Eionet CSV vocabulary—into a single structured artifact (`data/eagle_vocabulary.json`). If a local copy of the Eionet CSV is not supplied, the script fetches it directly from the Eionet repository.

During preprocessing, the script performs the following integration and normalization steps:

* **Schema Unification:** Consolidates each element's code, label, hierarchical level, parent identifier, matrix block (LCC, LUA, LCH), element type, formal definition, *Includes* and *Excludes* notes, thematic domains, and—where applicable—parameter measurement units.
* **Character Encoding Repair:** Sanitizes legacy encoding artifacts, such as Windows-1252 (`cp1252`) punctuation marks ingested as invalid control characters.
* **Hierarchy Reconstruction:** Derives parent-child relationships directly from the structured element codes (for example, linking `LCC-2_1_1` as a child of `LCC-2_1`).

### 2. Aligning with the EAGLE and ISO Data Models

Prior to implementation, the codebase of `eagle-iso-mapper` was analyzed to ensure full conceptual alignment with the EAGLE data model. This review established how the three matrix blocks, factor codes, and presence types map to bar code values, as well as how matrix columns translate into ISO `LC_Properties` and `LC_Characteristics`. Additional methodological constraints were incorporated from the bar coding documentation suite (the manual, thematic guidance, template, and existing bar-coded data inventories).

### 3. Layering a Curated Lexicon onto Vocabulary Labels

Official EAGLE labels are formal and technical (e.g., *Shrub Clearance*, *Commercial Crop Production*), whereas class descriptions typically rely on natural, descriptive phrasing (e.g., *bushes removed*, *arable land*, *rocky areas*, *minimum human interference*).

To bridge this gap without bloating the system, `eagle_eye/lexicon.py` defines a compact, auditable set of hand-crafted rules covering linguistic constructs absent from the raw vocabulary labels—such as negation cues, percentage ranges, height thresholds, degrees of *human influence*, and generic stopwords to ignore. Terms already represented in the vocabulary labels are matched automatically via lemmatized tokens, keeping the manual lexicon focused and transparent.

### 4. Establishing Regression Fixtures and Automated Tests

Both the standard CLC *Natural Grassland* definition and its extended CLC Illustrated Guide variant are stored as test fixtures in `tests/fixtures/`. An automated test suite of 115 tests continuously validates the prototype against the manual's worked benchmark, section-parsing logic, lexical variants, and end-to-end application workflows.

## Mapping Pipeline: From Prose to EAGLE Classes

The text-to-class pipeline is structured as a sequence of modular, transparent stages. Every automated decision retains its underlying rationale so the user interface can explain *why* a specific element or value was proposed.

1. **Candidate Spotting (`extractor.py`):** Both the curated lexicon rules and the preprocessed matrix labels scan the input text to generate candidate spans. When spans overlap, the longest and highest-scoring non-overlapping matches are retained. Matching is case-insensitive and leverages Snowball stemming, spelling normalization (e.g., *fertilised* = *fertilized*), and compound-head matching (e.g., *grassland* matching *grass*).
2. **Concrete Class Disambiguation (`resolver.py`):** Ambiguous spans (such as *mowing*) often map to multiple candidate elements. The resolver ranks candidates by computing TF-IDF similarity against Eionet definitions, applies *Excludes* notes as hard vetoes, and favors thematic domains and element families corroborated by the surrounding text. It descends into more specific child elements only when the text explicitly states distinguishing criteria. Confidence scores are derived from lexical evidence and whole-text context rather than isolated sentences, ensuring consistent resolution across phrasing variants (e.g., *grassland* vs. *Grasslands*).
3. **Section-Aware Interpretation (`sections.py`):** Structural headings from the CLC Illustrated Guide govern how subsequent text is interpreted: items under *excludes* are assigned `X` (unless explicitly claimed by the class), *generalisation* notes are treated as mapping guidance and excluded from scoring, and *particularities* are marked as optional.
4. **Bar Code Value Assignment (`barcode.py`):** Methodological rules from the bar coding manual are formalized at the clause level:
   * Explicit negation assigns `X` (*excluded*).
   * Qualifying phrases such as *may*, *e.g.*, or *such as* assign `1` (*optional*).
   * Disjunctive clauses (*A or B*) assign `2`.
   * Conjunctive clauses (*A and B*) assign `3`.
   * Threshold clauses (*at least two of*) assign `4`.
   * Exclusive clauses (*only A*) assign `5`.
   * Unqualified statements default to `3` (*defining*) and are explicitly flagged as *assumed*, reflecting the manual's requirement that only explicit wording is authoritative.
5. **Human-in-the-Loop Refinement (`overrides.py`, `analysis.py`):** Domain experts can reassign the EAGLE class of any highlight, annotate unhighlighted text spans, dismiss false positives, and adjust bar code values. Manual edits are anchored to text spans—automatically re-anchoring if the source text is edited—and are layered deterministically on top of the automated output (*automatic analysis followed by expert overrides*).

The pipeline outputs a structured *analysis* object comprising annotated text spans alongside detailed element entries (matrix block, confidence score, explanatory rationale, Eionet definition, and assigned BCV).

## Export Pipeline: From EAGLE Classes to ISO 19144-2 XML

An early prototype approach that generated custom XML directly was retired and replaced by a dedicated mapping prototype (`eagle-iso-mapper`) that bridges the EAGLE and ISO 19144-2 worlds using LinkML models and an SSSOM crosswalk. While `eagle-iso-mapper` is not (yet) an official standard tool provided by ISO or FAO, the LChS XML files it produces conform to the ISO 19144-2 LChS schema and import cleanly into the FAO LChS software.

Rather than serializing XML itself, `eagle_eye/isoexport.py` formats the finalized analysis as a **single-class EAGLE barcoding matrix** (using the vertical Excel layout with elements as rows and BCVs in a single column) and passes it to `eagle-iso-mapper`'s `run_eagle_to_iso_mapping` function, which applies its SSSOM crosswalk to generate the target LChS XML file.

Key architectural decisions in the export workflow include:

* **Single Source of Truth for Mapping Rules:** All schema transformations remain centralized within `eagle-iso-mapper`'s LinkML model and SSSOM crosswalk; EAGLE Eye is strictly responsible for generating the bar code matrix.
* **Accurate Representation of Excluded Elements:** Previously, the mapper translated BCV `X` as *Exclusive*, which misrepresented its semantics in ISO 19144-2. The upstream LinkML schema and generated models were extended with a `Precluded` presence type so that excluded elements are accurately preserved.
* **Transparent Coverage Reporting:** Because the mapper currently exports Land Cover Components and select characteristics (irrigation, rice, and hops) while omitting Land Use Attributes and other characteristics, the export dialog explicitly lists any omitted elements so users are never presented with a silently incomplete XML file.
* **Non-Blocking Initialization:** Because loading the LinkML and mapping libraries introduces noticeable latency, the mapper module is initialized in a background thread at application startup.

## User Interface Evolution

The web interface evolved iteratively through successive evaluations against the reference class descriptions:

* **v0.1:** Color-coded inline highlighting for LCC, LUA, and LCH spans with bidirectional click-to-highlight synchronization between text mentions and element entries.
* **v0.2:** Display of concrete resolved classes accompanied by confidence scores, decision rationales, and Eionet definitions derived from semantic similarity, hierarchy, and context.
* **v0.2.x:** Collapsible class detail panels that automatically scroll to and expand when a corresponding text highlight is selected.
* **v0.3.0:** Interactive expert overrides, automated BCV suggestions, and ISO 19144-2 LChS XML export.
* **v0.3.1:** Three-column workspace layout (source description, resolved classes, and highlight inspection), compact class pane with per-block slot allocation, inline reasoning tooltips, and streamlined visual chrome.
* **v0.3.2:** Support for CLC Illustrated Guide sections, lexical variants, Snowball stemming, and the *human influence* rule set.
* **v0.3.3:** Externalized example definitions loaded dynamically from `config/examples`.

## Known Limitations

* **Strict Textual Dependence:** Confidence scores measure how clearly the input phrasing identifies an element; ambiguous or underspecified wording yields low-confidence suggestions. In accordance with the bar coding manual, the system never infers concepts not explicitly stated in the text.
* **Assumed Defining Values:** Assigning BCV `3` to plain, unqualified statements is a heuristic default and is explicitly labeled as *assumed* for expert verification.
* **Sensitivity to PDF Extraction Artifacts:** Section detection relies on standard guide headings; pasting raw text from PDFs with interleaved figure captions or layout noise can disrupt section boundaries.
* **Scope of *Applicable For* Clauses:** Alternatives listed under *applicable for* headings in the CLC guide are not currently parsed as mutually exclusive (`either-or`) conditions.
* **Upstream Export Coverage:** ISO 19144-2 XML output is bounded by the element types currently supported by `eagle-iso-mapper` (as detailed in the export section above).
